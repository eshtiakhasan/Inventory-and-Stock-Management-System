## Overview

**Page Purpose:** Let a Manager start a Stock count at one Warehouse for all Products, one category or a chosen list, assign the counters, watch each line get counted **without seeing counts or system quantities while it runs**, close the count with one confirm, and see the result: matched lines "verified", mismatches turned into **Discrepancy cases** with "Open to decide" (FR-34, FR-36, FR-37).

**User Situation:** Rafiq, the inventory manager, Saturday morning at his desk, plans the weekly count of the rice and oil aisle at Narayanganj with two workers, Karim and Rahim. He hopes to know which numbers he can trust and fix the rest this week. He worries about a count nobody trusts, or mismatches with no trail ([scenario 08](../08-rafiq-runs-the-weekly-count.md), Q3-Q4; [Trigger Map → Manager](../../../B-Trigger-Map/trigger-map.md)). (Rafiq is an illustrative name; the PRD leaves the Manager unnamed.)

**Success Criteria:**
- Starting a 20-Product count with two counters takes one form and one button; the counters see "Stock count SC-015" in My tasks at once (FR-34, FR-53).
- While the count runs, Rafiq sees which lines are counted, by whom and when, but **no quantities**, so the count stays blind even if he counts too (FR-35, DD-7).
- Close count is one confirm that states what will happen in one sentence, and warns when a counter still has lines not received by the server (Interaction Primitives → Confirm vs undo; DD-6).
- At close, and only then, every line is either "verified" (today becomes its last verified date) or a Discrepancy case with counted vs On hand, the counter and the times; shortages move to Unexplained at that moment, never deleted (FR-36, FR-37, DD-6).
- A line that arrives after close never changes the closed count; it becomes a "Late count line" Issue for the Manager who started the count (DD-6).
- Rafiq can open each case to decide; on a line he counted himself he is told someone else must decide (FR-5).
- Business: accuracy is measured weekly (SM-1, shown as "matched lines"), and counting stays a habit (SM-C1).

**Entry Points:**
- Desktop side nav "Counts"; phone tab "Counts" (Manager) (EXPERIENCE.md → Home and navigation per Role).
- A Sync conflict decision "Recount · open a count" creates a one-Product count that appears here ([03.2](../../03-nasima-clears-the-inbox/03.2-issue-detail/03.2-issue-detail.md)).
- "Last verified … · SC-014" link on [07.2 Product stock](../../07-tanvir-promises-stock-while-the-customer-waits/07.2-product-stock/07.2-product-stock.md) → that count's results.
- Owner view drill-down rows name the Stock count that found a case ([04.1](../../04-haque-traces-an-unexplained-loss/04.1-owner-view/04.1-owner-view.md)).

**Exit Points:**
- Start count → counters' My tasks show the count card → [08.2 Count lines](../08.2-count-lines/08.2-count-lines.md) on their phones (scenario's next step).
- Results: "Open to decide" on a Discrepancy case → [03.2 Issue detail](../../03-nasima-clears-the-inbox/03.2-issue-detail/03.2-issue-detail.md), Found or Confirmed loss with a Reason (UJ-7 step 6).
- Product name in results → [07.2 Product stock](../../07-tanvir-promises-stock-while-the-customer-waits/07.2-product-stock/07.2-product-stock.md).
- Issues inbox ([03.1](../../03-nasima-clears-the-inbox/03.1-issues-inbox/03.1-issues-inbox.md)) also lists the new cases.

## Technical Notes

- **Blind data rule (FR-35, DD-7):** while a count is open, the progress API returns no counted quantities and no On hand for its lines to anyone (the Manager may also be a counter). Quantities appear only in results after close. Assigned counters also get "Hidden during count" for these Products at this Warehouse on every other screen (07.1, 07.2, 04.2, scan results).
- **Stock posting (DD-6, the count exception in DD-1):** each Save line on 08.2 records counter, quantity and time (queued offline like any floor action) but moves no stock. Close count compares each line with On hand as of the moment it was counted (FR-36), posts the shortage moves to Unexplained, opens Discrepancy cases, marks matches verified, raises Dispatch-short Issues where Reserved was taken, and closes the task.
- **Unsynced lines warning (DD-6):** the dialog needs each counter's phone to report how many count lines it holds unsynced for this count (sent whenever the phone is online). A phone offline since it saved cannot report, so the warning reflects the last report (Open Question 17).
- **Late lines (DD-6):** a count line received after close is stored with the count but does not change its results; the server opens a Late count line Issue for the starting Manager.
- **Segregation of duties (FR-5):** server refuses a Discrepancy case decision by the line's counter; the UI hides Open to decide for those rows and shows the sentence.
- **Value (FR-4, DD-2):** shortage / surplus taka = difference × Unit cost at the moment counted (FR-18); returned only to value Roles.
- **Duplicate safety (FR-14):** action IDs on Start count and Close count.
- **Accessibility:** desk structure (skip link, `nav`, `main`, one H1, focus to H1 on route change); tables use `th` with `scope`; on phone rows become labelled cards. Progress updates via polite region at most once a minute. Dialog focus on Go back.
- **URL state:** `/counts?status=…`, `/counts/new`, `/counts/{id}`.
